## Contract and ownership boundary

`ResetAsync` owns every runtime that was current, parked, dequeued, or dispatched before its ownership snapshot. It waits for those disposals to finish, while disposal remains best-effort, exactly once, and outside synchronization locks. Relative to retired-runtime disposal, ordinary credential rotation remains nonblocking: `GetAsync` registers background disposal without awaiting that disposal. A `GetAsync` overlapping an explicit reset waits for that reset generation before constructing or returning a runtime; caller cancellation cancels only that waiter and never the shared reset.

The implementation uses a private ownership monitor for graveyard dequeue/enqueue and dispatched-task publication/snapshot, plus an active-reset generation marker. Ownership transitions are atomic with respect to the monitor. Lock ordering is `_gate` followed by the ownership monitor when both are required; sweep takes only the ownership monitor. Runtime disposal is not invoked or awaited by code while it holds either synchronization lock; dispatch may schedule the disposal task while the ownership monitor is held, and `GetAsync` may perform its ordinary factory/gate awaits outside the disposal ownership critical section.

Overflow and outside-gate sweep both register the exact dispatched disposal task while holding the ownership monitor. Reset drains the graveyard and snapshots dispatched tasks in one monitor transaction, so a runtime cannot fall between queue ownership and task ownership. Completion bookkeeping removes only the completed task; it never redisposes the runtime. Reset clears its matching generation marker under `_gate` before signaling waiters outside the gate.

## Limits and follow-up

This bounded repair does not impose a total active-disposal or resource cap. It does not provide an exhaustive sweep/reset race proof, generalized concurrent stress proof, live plugin validation, or six-repository zero-findings result. Those remain separate requirements. The existing `CreateAsync(settings, cancellationToken).ConfigureAwait(false)` await still occurs while `_gate` is held; this unchanged gate-held factory latency/reentrancy concern remains H3 follow-up debt and is not cleared by the reset wait moving outside `_gate`. The audit also does not expand the disposal exception policy: individual disposal failures remain swallowed so one disposer cannot prevent the remaining drain.
